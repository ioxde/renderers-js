Drop the `programAddress` config parameter from PDA finders that nothing overrides. A generated `find*Pda` function is pinned to the program the client was generated for, so its optional `config: { programAddress?: Address }` parameter had exactly one valid value — the one already baked into the function. Those finders now take only their seeds, or no arguments at all when the PDA has no variable seeds, and inline the program address directly into `getProgramDerivedAddress`.

Finders that a use-site actually derives under a runtime program keep the parameter unchanged. A PDA qualifies only when a `pdaValueNode` links to it, resolves its program through an account or argument reference, and the linked `pdaNode` carries no `programId` of its own. The reference alone is not enough: Codama resolves it ahead of time whenever the referenced account is address-constrained, stamping the result onto the PDA definition while leaving the reference in place, so the parameter would again have exactly one legal value. Raydium's AMM migration instructions are that shape — `ammProgram` is address-constrained on-chain, so `findAmmAuthorityPda` and its siblings are now called bare. Inline `pdaNode` defaults never constrained the finder because the renderer derives those addresses inline; they now prefer a resolved pin over the runtime reference too, matching the linked case.

Make the parameter required on the finders that do keep it. The whole point of that residual case is that the deriving program is genuinely unknown at generation time, so there is nothing to default to — falling back to the program the client was generated for would silently derive an address under the wrong program. The signature is now `config: { programAddress: Address }` with no default, and the body destructures it rather than supplying a fallback. Generated call sites pass one either way: a use-site with a runtime program reference forwards it, and a use-site that does not override the PDA forwards the enclosing program, which is exactly what an un-overridden `pdaValueNode` derives under. An account whose `pda` link lands in this category is now a generation-time error instead of uncompilable output, because its decoder guards ownership against the program being rendered while its address derives under another program; the error names the account and the PDA and points at the two ways out, which are pinning the PDA's `programId` or address-constraining the referenced account.

Reference the generated program constant instead of inlining its address. A finder for a PDA of the program being rendered now emits `PROGRAM_NAME_PROGRAM_ADDRESS` imported from the generated `programs` barrel, both as the `programAddress` argument and inside any program-ID seed, so the address has a single source of truth in the generated client — the same thing the Rust renderer does with `use crate::<PROGRAM>_ID;`. A PDA pinned to some other program keeps its address inline, since no constant exists for a foreign program and minting one per PDA is not worth it. This adds a `pdas` to `programs` import edge, which is safe: a generated program page contains only its address constant and imports nothing from the rest of the client.

This is breaking for any caller that passed a config object to a finder that no longer takes one, for callers that relied on the parameter's position, and for callers that omitted the config on a finder where it is now required. To target a different deployment, regenerate the client against that program address rather than overriding it at the call site.
