Resolve PDAs whose seeds are all constant at generation time and export their address. When every seed of a PDA is a constant this renderer can encode itself and the deriving program is known while rendering, the address is the same on every call, so there is nothing to compute at runtime. Such a PDA now emits an exported `NAME_PDA_ADDRESS` constant next to its finder, and the finder returns that constant with its bump instead of hashing seeds through `getProgramDerivedAddress`. The derivation mirrors Solana's `find_program_address` — descend from bump 255, sha256 over the seeds, the bump, the program address and the `ProgramDerivedAddress` marker, and take the first candidate that is not on the ed25519 curve — so the emitted address is byte-for-byte what the runtime call produced. This is the same thing the Rust renderer does, and both renderers produce identical constants from identical IDLs.

The finder becomes synchronous. It still returns a `ProgramDerivedAddress`, so `const [address, bump] = findFooPda()` gives the same tuple it always did, but it no longer returns a promise: there is no derivation left to wait for, and a signature promising one would lie about the work behind it. Callers who want the address on its own can skip the finder entirely and import the constant. Generated instruction builders do exactly that — an account defaulting to a resolved PDA is now assigned the constant — except for an account whose bump the instruction also reads, which keeps calling the finder because the bump reader needs the whole tuple rather than a bare address.

Nothing is resolved unless the renderer can be certain of the result. A single variable seed, a seed whose codec writes anything beyond the value itself such as a size prefix or a fixed size, a program address that does not decode to thirty-two bytes, a seed over the thirty-two byte limit, or more than sixteen seeds all fall back to deriving at runtime exactly as before. Finders that keep a `programAddress` parameter because a use-site derives them under a program only known at runtime are excluded by construction: their address depends on what the caller passes.

Instructions whose only asynchronous work was one of those finders no longer render an async builder at all. A `get*InstructionAsync` function and its `*AsyncInput` type exist to let a builder await something; once every default it applies resolves at generation time, the async variant would be the sync one with a promise wrapped around it. Those instructions now render only `get*Instruction`, and because the sync builder can apply defaults it previously had to skip, the accounts behind them move from required to optional on the sync input type. An instruction that still has an async resolver, an async byte delta or remaining accounts, or a PDA that genuinely derives at runtime keeps its async variant untouched.

This is breaking for generated clients in three ways. A finder that used to hash on every call now returns a constant, so anything that stubbed, spied on or timed `getProgramDerivedAddress` through a finder no longer observes it. Awaiting a finder for a resolved PDA is now awaiting a plain value, which still works but no longer needs the `await` and will be flagged by lint rules such as `@typescript-eslint/await-thenable`. And callers of a `get*InstructionAsync` function that no longer exists must move to the synchronous builder of the same name minus the suffix, dropping the `await` with it.

Two customisation hooks need attention when they point at a resolved PDA. A module named by `linkOverrides.pdas` is now expected to export the address constant as well as the finder, because a folded use-site imports `NAME_PDA_ADDRESS` from it, and a use-site that resolves without folding calls the hand-written finder without awaiting it — both fail loudly at compile time rather than silently, but both need the hand-written module updated. A custom resolver reading `scope.accounts.foo.value` for a folded account now receives a bare `Address` where it previously received the `[address, bump]` tuple, so a resolver indexing `[1]` for the bump has to derive it another way; the renderer keeps the tuple when an `accountBumpValueNode` reads the bump, but it cannot see inside a resolver body to know one is needed.

An account defaulting to a resolved PDA also gets a sharper type parameter. Where it previously widened to `TAccountAuthority extends string | AccountMeta<string> = string`, it now names the address itself, the same way an account defaulting to a fixed program already named that program. The rendered instruction type therefore carries the real PDA rather than `string`, so the address survives into anything generic over it. This tracks whether the PDA resolved at all rather than whether the builder folded it to a constant, since an account whose bump is read holds that same one address and merely keeps the tuple the bump comes out of.

Naming the address narrows one thing, so it is the fourth way this is breaking. An instruction type written with fewer arguments than it has parameters now falls back to the pinned address for that account, which means an instruction built with a different one stops assigning to it — `CollectFeeInstruction<typeof RAYDIUM_LAUNCHPAD_PROGRAM_ADDRESS>`, or a bare `CollectFeeInstruction` used as an array element or a function parameter, no longer accepts an authority other than the PDA. Inference is untouched, so a caller who passes a different address still has the parameter inferred from what they passed rather than pushed to the default, and omitting the account is unaffected. Accounts defaulting to a fixed program have behaved exactly this way for as long as they have been pinned; this only brings resolved PDAs into line with them.

The renderer itself picks up `@noble/hashes` and `@noble/curves` as dependencies for the sha256 and curve check the derivation needs. Both are portable, so the browser and React Native bundles are unaffected and stay fully tree-shakeable.
