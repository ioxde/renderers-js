Guard the generated parse and decode helpers against data they were not meant to read. Anchor discriminators derive from names alone, so byte-identical discriminators recur across programs, and within one program siblings often share a layout — `buyExactIn` and `sellExactIn` are both a discriminator plus three `u64`s. Previously `parse<Ix>Instruction` on either a foreign or a sibling instruction returned a well-typed wrong parse, and `decode<Account>` decoded garbage, since kit's fixed-size decoders tolerate trailing bytes. Both now check the program and the discriminator.

The guards are always emitted — there is no renderer option to disable them — and each site keeps the semantics its return type implies. `parse<Ix>Instruction` throws on a program mismatch via kit's `assertIsInstructionForProgram` (a catchable `SolanaError` with `SOLANA_ERROR__INSTRUCTION__PROGRAM_ID_MISMATCH`), then on a discriminator mismatch, both ahead of its account-metas check so a mis-routed instruction reports the real problem rather than a misleading meta count. `decode<Account>` throws on a foreign owner, then on a discriminator mismatch, both inside an `exists` narrowing so the `{ address, exists: false }` variant — which carries neither a `programAddress` nor data — still returns unthrown. The aggregate `parse<Program>Instruction` and the `identify<Program>*` helpers instead return `null`, because callers iterate whole transactions where other programs are ordinary rather than erroneous. All account fetch helpers funnel through `decode<Account>`, including the program plugin's self-fetch methods, which now delegate to those helpers rather than decoding through kit's `addSelfFetchFunctions`.

The two new throws are an `Error` with a stable `name` — `AccountDiscriminatorMismatchError` and `InstructionDiscriminatorMismatchError`, siblings of `AccountOwnerMismatchError`. Match the name, not the message, which names the decode or parse function, the expected type and — for accounts — the address, so mis-routed indexer code is diagnosable. The instruction side does not reuse kit's `SOLANA_ERROR__PROGRAM_CLIENTS__FAILED_TO_IDENTIFY_INSTRUCTION`: it states the instruction could not be identified as one of the program's, which is false in exactly the guarded case, and its context cannot name the expected instruction.

The discriminator check is emitted only where a constant is known, the same condition that gates the `*_DISCRIMINATOR` constants: constants always, fields only with a value default, sizes never — so a size-discriminated node renders no check rather than turning `decode` into a length assertion. It reuses the `containsBytes` conditions behind `identify*` at each discriminator's own offset, so guards and identifiers cannot disagree, and because `containsBytes` compares against a clamped slice, data shorter than a discriminator is a mismatch rather than a range error. An instruction with a discriminator but no arguments renders no check, since its parsed type carries no `data` field.

The `identify<Program>*` object argument now requires a `programAddress` field, so an object caller cannot resolve the same bytes differently depending on the shape they passed; callers holding only raw bytes keep passing them directly, which opts out explicitly. The account helpers accept an expected-owner override for forks and redeployments: `decode<Account>` takes an optional trailing `programAddress`, `fetch<Account>`/`fetchMaybe<Account>` and `fetchAll<Account>`/`fetchAllMaybe<Account>` accept `config.programAddress`, and the `FromSeeds` variants forward it into the owner check. Each fetch helper destructures the override off its config before the RPC call rather than forwarding the config whole: `FetchAccountConfig`/`FetchAccountsConfig` have no such field, and kit spreads whatever remains straight into the `getAccountInfo`/`getMultipleAccounts` params, so an override left in would be sent to the RPC node. The discriminator check is independent of that override — an override still requires the account to be the one being decoded.
