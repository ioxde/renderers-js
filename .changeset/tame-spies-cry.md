Pin generated clients to the program address they were generated for. The instruction builders no longer accept `config: { programAddress }` and no longer carry a `TProgramAddress` type parameter, and the account helpers no longer accept an expected-owner override: `decode<Account>` drops its trailing `programAddress` parameter and the `fetch`/`fetchMaybe`/`fetchAll`/`fetchAllMaybe`/`*FromSeeds` helpers take kit's `FetchAccountConfig`/`FetchAccountsConfig` unmodified. To target another deployment, regenerate with a different address via `updateProgramsVisitor({ myProgram: { publicKey } })`.

The runtime override could only ever be threaded partially, which made it a source of silent misderivation rather than a way to retarget a client. A builder resolved its accounts, its account metas and its emitted `programAddress` from the override, but the PDA finders it called did not take part: `find<Pda>` defaults to its own baked-in constant, and the builder never forwarded the override into it. Passing `{ programAddress: fork }` to `getCreateAssociatedTokenInstructionAsync` therefore produced an instruction routed to the fork whose `ata` was derived under the canonical associated-token program, which fails on-chain as a seeds-constraint or account-not-found error rather than as a configuration error. Overriding the expected owner on the account side had the same shape: `fetch<Account>FromSeeds` forwarded it into the derivation, but nothing tied it to the address the caller had used to build the instruction that created the account. Because the program address is a generation-time fact for every other part of a generated client, making it a per-call parameter in these two places could not be made coherent — only removed.

Two things are deliberately kept. `find<Pda>(seeds, config)` still accepts a program address, because a PDA's deriving program can genuinely vary per call when the IDL says so — a `pdaValueNode` whose `programId` is an instruction account resolves to whatever the caller passed for that account, which no amount of generation-time substitution can express. And the owner and discriminator guards in `decode<Account>` and `parse<Ix>Instruction` are unchanged; they now compare against the program constant directly.

This also fixes a latent bug in the generated program plugin, which passed its `input` object to builders that take no parameters. That argument previously landed in the now-removed `config` slot and was silently ignored. Plugin methods for instructions with no accounts and no caller-supplied arguments now take no parameter, matching their builders.
